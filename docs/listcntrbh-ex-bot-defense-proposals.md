# ListCntrbHExHandler() に対する Bot 対策案（設計メモ）

作成日: 2026-09-22
対象: SRCGI

---

## 1. 前提

この文書は、実装を確定するものではなく、

- 対策候補の整理
- どの層で何を入れるべきか
- どこまでが妥当か

を比較するための設計メモです。

ソース修正は行わず、適用可否は後で判断する前提です。

---

## 2. 何が問題か

`ListCntrbHExHandler()` は、DB からデータを取得してページを生成するタイプのハンドラです。

- パラメータに `eventid`, `userno`, `tlsnid`, `name`, `ie` などがある
- これらの組み合わせが増えると URL の総数が大きくなる
- 画面遷移の最終地点になりやすい
- ボットが巡回しやすい構造になっている可能性が高い

このため、単に一つのハンドラに対してだけ埋め込むのではなく、

- 上流での経路制御
- 共通 middleware での制限
- ハンドラ自体の最終防衛

の 3 つを合わせて見るべきです。

---

## 3. 画面遷移の観点

実際の到達経路としては、以下のような流れが想定されます。

```text
TopHandler
  └─ CurrentEventsHandler
      └─ ListLastHandler
          └─ ListCntrbExHandler
              └─ ListCntrbHExHandler
```

この見方で対策を考えると、最終ハンドラだけではなく、

- どの画面からそのハンドラが起動されるか
- どの入口がアクセスを増やしているか
- 上流の画面でリンクの性質を制限できるか

を見て対策を設計できます。

---

## 4. 対策案のカテゴリ

### 4.1 共通 middleware 側の対策

該当箇所: [main.go](../main.go#L288-L430)

候補:

- IP 単位の Rate Limit
- User-Agent 判定
- Bot 判定
- 典型的なアクセスパターンの制御
- リクエストの集中度を監視して抑制

利点:

- 全ハンドラに効く
- 入口で大量アクセスを止められる
- 最終ハンドラへの負荷を減らせる

注意点:

- 健全なアクセスまで抑えすぎると障害の可能性がある
- リアルユーザーの正常遷移を誤判定しないようにする必要がある

---

### 4.2 遷移の上流での対策

該当箇所:

- [ShowroomCGIlib/HandlerTop.go](../ShowroomCGIlib/HandlerTop.go#L41-L151)
- [ShowroomCGIlib/HandlerCurrentEvents.go](../ShowroomCGIlib/HandlerCurrentEvents.go#L93-L195)
- [ShowroomCGIlib/HandlerListLast.go](../ShowroomCGIlib/HandlerListLast.go#L74-L176)
- [ShowroomCGIlib/HandlerListCntrbEx.go](../ShowroomCGIlib/HandlerListCntrbEx.go#L103-L220)

候補:

- 通常画面遷移で必要なパラメータだけを許可する
- 直接 URL を叩いてアクセスするケースを制限する
- 画面遷移に必要な参照条件を明示する
- 大量の順番アクセスに対して停止条件を追加する

利点:

- ボット型の巡回を自然な画面遷移と分離しやすい
- 最終ハンドラに入る前に対策できる

注意点:

- 画面遷移の自由度を落としすぎると UI の使い勝手が悪化する
- 一部の正常利用を誤って阻害する可能性がある

---

### 4.3 最終ハンドラ自体の対策

該当箇所: [ShowroomCGIlib/HandlerListCntrbHEx.go](../ShowroomCGIlib/HandlerListCntrbHEx.go#L115-L260)

候補:

- Turnstile の適用
- 一定条件を満たす場合だけ許可
- `eventid` や `tlsnid` の妥当性を厳密に検査
- 一覧取得件数の上限設定
- 重複クエリの抑制
- CPU / DB 負荷の高い組み合わせを明示的に拒否

利点:

- 直接的な最終防衛になる
- 直接アクセスされても止められる

注意点:

- 最終ハンドラが重いので、そこに対策を集中させると負荷も集中しやすい
- 上流で止められなかった場合の最後の砦として位置づけるべき

---

## 5. 候補として考えられる具体的なルール

以下は「設計案」としての例であり、適用可否は別判断です。

### 5.1 最低限のルール

- bot と判定されたアクセスは、`ListCntrbHExHandler()` への到達を止める
- `eventid` が存在しない場合は早期終了する
- `userno` / `tlsnid` の組み合わせ不正は拒否する
- 同一のアクセスが短時間内に多数来た場合はレート制限をかける

### 5.2 上流でのルール

- `ListCntrbHExHandler()` の前段に、必須パラメータの存在チェックを強化する
- 画面遷移の正常順序を確認する
- 直接 URL 入力で飛んできたアクセスを別扱いにする

### 5.3 大規模探索対策

- 一度に大量の履歴を取るアクセスを制限する
- 過去のページ数が巨大になりそうなクエリを拒否する
- 重いパラメータ組み合わせに対して絞り込み条件を設ける

---

## 6. 実装優先度の提案

以下の順で見るとバランスがよいです。

### 優先度 A: すぐに検討価値がある

- 共通 middleware の bot / rate limit 強化
- `ListCntrbHExHandler()` の直接アクセスに対する Turnstile / レート制限
- 不正な `eventid` と `tlsnid` の検証

### 優先度 B: 実装する価値があるが慎重に判断

- 上流の遷移制御
- 画面からの遷移順チェック
- 特定のパラメータ組み合わせの重い呼び出しを禁止する仕組み

### 優先度 C: 将来の拡張候補

- キャッシュ導入
- 高コストパラメータを事前にサマリ化するです
- 生成結果の再利用
- 監視・ログからアクセス傾向を分析して自動制御する仕組み

---

## 7. 設計上の重要な結論

今回の対策の中心は、

- 直接のボット対策だけでは不十分
- 画面遷移の経路を見て、入口と上流を制御することが重要
- 最終ハンドラは最終防衛として使うのが自然

という整理です。

`ListCntrbHExHandler()` は、単一の「問題のある URL」ではなく、

- 画面遷移の最終地点
- 生データ生成の重い処理
- 多様なクエリパラメータがあり得る

という性質を持っているため、対策は複数層で行うのが妥当です。
